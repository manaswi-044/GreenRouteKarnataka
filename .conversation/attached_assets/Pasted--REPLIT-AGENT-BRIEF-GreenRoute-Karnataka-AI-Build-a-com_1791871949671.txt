## 1. APP OVERVIEW

**Name:** GreenRoute Karnataka AI

**One-liner:** An AI travel planner that recommends Karnataka attractions, builds a personalised day-by-day itinerary, and compares the cheapest, fastest, greenest and best-balanced multimodal routes between stops. It re-plans instantly when budget, time or preferences change.

**Problem it solves:** Travellers in Karnataka struggle to decide (a) where to go, (b) how to sequence places sensibly by day, (c) how to get between them cheaply and sustainably, and (d) how to adjust when plans change. Existing tools handle only one of these. Public transport and CO₂ impact are almost never shown.

**Target users:** Domestic and international tourists (students, backpackers, families, eco-conscious travellers) planning 1–7 day trips in Karnataka from a city such as Bengaluru, Mysuru or Mangaluru.

**Hackathon framing:** Problem Statement 6, "AI Travel Planner for Karnataka". The pitch is: *"We don't just tell you where to go. We tell you where to go, what to do each day, how to get there, and which option best fits your budget, time and planet."*

## 2. FULL FEATURE LIST (priority order)

### P0: Core (must work flawlessly)
1. **Tourist-place recommender.** Interest-based ranking of 35+ curated Karnataka attractions. Interests: History, Nature, Waterfalls, Beaches, Temples, Adventure, Food, Wildlife, Hidden Gems. Each result shows a match score and a "why recommended" line.
2. **Personalised itinerary planner.** Inputs: starting city, number of days (1–7), total budget (₹), interests (multi-select), travel pace (Relaxed / Balanced / Packed), transport preference (Cheapest / Fastest / Greenest / Balanced), and walking tolerance (Low / Medium / High). Output is a day-by-day plan with ordered stops, visit durations, timings, and per-day and total cost.
3. **Multimodal route optimiser.** For every leg between consecutive stops, generate options using Walk, Local Bus (KSRTC/BMTC), Namma Metro (Bengaluru only), Train (between rail-connected hubs), Auto, Cab and E-Cab. Compute cost (₹), time (min) and CO₂ (kg) per option. Select the best option per leg for each of 4 strategies: **Cheapest, Fastest, Greenest, Balanced**.
4. **Cost / Time / Emissions comparison dashboard.** A 4-column strategy comparison with bar charts, a "winner" badge per metric, and a CO₂-saved-vs-all-cab baseline.
5. **Adaptive replanning.** A "Change my plan" panel with a budget slider, days slider, walking tolerance, and strategy switch. Re-running the planner shows a diff ("Removed: X, Swapped bus→metro, Saved ₹820"). Includes a natural-language box ("I only have ₹3000 now and hate walking").
6. **Interactive map (Leaflet + OpenStreetMap).** Numbered markers per day (colour-coded per day), route polylines colour-coded by transport mode, popups, fit-to-bounds per day, and layer toggles.

### P1: Impressive extras
7. **Budget-overrun assistant.** If the plan exceeds budget, show a banner with 3 one-click fixes (e.g. "Drop Jog Falls → saves ₹1,150", "Switch to greenest transport → saves ₹640", "Cut 1 day").
8. **Eco Score** (0–100) for the whole trip, with an animated gauge and an equivalent such as "= 6 trees' daily absorption".
9. **Live weather per stop and day** (Open-Meteo, free). If heavy rain is forecast, flag outdoor stops with a ⚠️ and suggest an indoor swap.
10. **Place detail drawer.** Photo (Wikipedia API), description, entry fee, best months, time needed, tags and "Add to / Remove from itinerary".
11. **Save / load trips** (localStorage) and **shareable summary + Print/PDF** (`window.print()` with print stylesheet).
12. **AI narrative.** A short friendly summary per day ("Day 1 blends Hoysala art with …"). If `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` env var is set, call the LLM. Otherwise use template-based text.

### P2: Nice-to-have
13. Lesser-known / hidden-gem toggle that boosts offbeat places.
14. Dark mode toggle.
15. Seasonal "best time" badge per place, based on the travel month chosen.
16. Animated hero with a typed tagline and a Karnataka map silhouette.

## 3. TECH STACK

Single repo, one Replit project, two parts:

- **Frontend:** React 18 + Vite + TypeScript, Tailwind CSS, `react-router-dom`, `zustand` (state), `react-leaflet` + `leaflet`, `recharts` (charts), `framer-motion` (animations), `lucide-react` (icons), `clsx`, `date-fns`.
- **Backend:** Node.js + Express + TypeScript (`tsx` to run), `cors`, `zod` (validation), `node-cache` (in-memory caching of external API calls). Backend serves `/api/*`. In production the frontend build is served statically from Express. Configure the Vite dev server to proxy `/api` to the Express port.
- **Data:** Static JSON files in `/server/data` (no database). Trips are saved client-side in `localStorage`.
- **Optional AI:** use `fetch` directly against the Anthropic or OpenAI REST API if the env var exists. Wrap in try/catch with a 6s timeout and always fall back to templates.
- **Free external services (no keys):** OSRM public demo server, Open-Meteo, Wikipedia REST API, OpenStreetMap/CARTO tiles. All external calls go through the backend with caching and graceful fallbacks, so the demo never breaks if a service is down.
- **Run command:** `npm run dev` runs both with `concurrently`. Expose the web app on port 5173 (or whichever Replit maps) and the API on 3001.

### 6.1 TypeScript data models (put in `/shared/types.ts`)

```ts
type Interest = 'history'|'nature'|'waterfalls'|'beaches'|'temples'|'adventure'|'food'|'wildlife'|'hidden-gems';
type Mode = 'walk'|'metro'|'bus'|'train'|'auto'|'cab'|'ecab';
type Strategy = 'cheapest'|'fastest'|'greenest'|'balanced';

interface Place {
  id: string; name: string; region: string; hub: string;      // hub = nearest start-city hub id
  lat: number; lng: number;
  tags: Interest[]; hiddenGem: boolean;
  fee: number;            // INR per Indian adult
  visitHrs: number;       // typical time on site
  bestMonths: number[];   // 1-12
  outdoor: boolean;
  wiki: string;           // Wikipedia page title for photo/summary
  desc: string;           // 1–2 sentences
  metroStation?: string;  // Bengaluru only, id from metro stations
}
interface Hub { id: string; name: string; lat: number; lng: number; railConnected: boolean; metro?: boolean; }
interface TripInput {
  startHub: string; days: number; budget: number; interests: Interest[];
  pace: 'relaxed'|'balanced'|'packed'; priority: Strategy;
  walking: 'low'|'medium'|'high'; month: number; hiddenGems: boolean;
  mustVisit?: string[]; excluded?: string[];
}
interface LegOption { mode: Mode; modes?: Mode[]; distanceKm: number; minutes: number; cost: number; co2Kg: number; label: string; }
interface Leg { fromId: string; toId: string; options: LegOption[]; chosen: Record<Strategy, LegOption>; geometry?: [number,number][]; }
interface Stop { place: Place; arrive: string; depart: string; matchScore: number; why: string; weather?: {tMax:number; rainMm:number; code:number}; }
interface Day { dayNo: number; stops: Stop[]; legs: Leg[]; entryCost: number; foodCost: number; stayCost: number; narrative: string; }
interface Itinerary {
  input: TripInput; days: Day[];
  totals: Record<Strategy, {cost:number; minutes:number; co2Kg:number; modeMix:Record<Mode,number>}>;
  baselineCo2Kg: number; ecoScore: number; overBudgetBy: number; suggestions: Suggestion[];
}
```

Mode rules per leg:
- **Walk:** only if distance ≤ walkMaxKm for the chosen tolerance.
- **Metro:** only if both places have `metroStation` (or a walkable station within 1.2 km) and both are in the Bengaluru metro dataset. Compose as walk + metro + walk, adding walk minutes.
- **Train:** only if the leg is inter-hub (> 80 km), both hubs are `railConnected`, and the pair appears in the rail-pairs list. Compose as local leg to the station (auto/bus) + train + local leg.
- **Bus / Auto / Cab / E-Cab:** always available (E-cab only within Bengaluru, Mysuru and Mangaluru hubs or for ≤ 80 km).

### 6.7 Free APIs to integrate (all through backend proxy routes with caching)

1. **OSRM routing (no key):**
   `GET https://router.project-osrm.org/route/v1/driving/{lng1},{lat1};{lng2},{lat2}?overview=full&geometries=geojson`
   → use `routes[0].distance` (m), `routes[0].duration` (s), `routes[0].geometry.coordinates` (array of `[lng,lat]`; flip to `[lat,lng]` for Leaflet). Timeout 5s. Cache by coordinate pair for 24h. On failure, use the Haversine × 1.3 estimate and a straight-line polyline. Never block the UI.
2. **Open-Meteo forecast (no key):**
   `GET https://api.open-meteo.com/v1/forecast?latitude={lat}&longitude={lng}&daily=temperature_2m_max,precipitation_sum,weathercode&timezone=Asia%2FKolkata&forecast_days=7`
   → flag a stop if `precipitation_sum` ≥ 15 mm and `outdoor` is true. Cache 1h. Skip silently on failure.
3. **Wikipedia REST summary (no key):**
   `GET https://en.wikipedia.org/api/rest_v1/page/summary/{wiki_title_url_encoded}`
   → use `thumbnail.source` for the photo and `extract` as the description override. Cache 7d. Fallback to a gradient with an emoji if no thumbnail.
4. **Map tiles:** CARTO Voyager `https://{s}.basemaps.cartocdn.com/rastertiles/voyager/{z}/{x}/{y}{r}.png` with OpenStreetMap + CARTO attribution.
5. **Optional LLM (only if env var is set):** Anthropic `POST https://api.anthropic.com/v1/messages` (header `x-api-key`, `anthropic-version: 2023-06-01`) or OpenAI chat completions. Use for (a) daily narratives and (b) parsing natural-language replans into JSON `{budget?, days?, walking?, priority?, excludeInterests?}`. Fallback is templates plus a regex parser (`₹?(\d[\d,]*)`, "less/no walking", "greenest", "fastest", "cheaper", "1 less day").

## 7. CORE ALGORITHMS (implement exactly; deterministic and explainable)

**A. Recommendation score (0–100) per place:**
```
interestMatch = |place.tags ∩ user.interests| / max(1, |user.interests|)       (0–1)
score = 60*interestMatch + 15*(hiddenGemsOn && place.hiddenGem ? 1 : 0)
      + 10*seasonFit (1 if month in bestMonths else 0.3) + 10*feeFit (1 - min(1, fee/ (budget/ (days*3))))
      + 5*proximity (1 - min(1, haversine(startHub, place)/600km))
mustVisit → +100 ; excluded → remove
```

The `why` text = "Matches your interest in {tags}, best in {month}, ₹{fee} entry".

**B. Itinerary construction:**
1. Rank places by score. Take the top N = `days × stopsPerDay[pace]` candidates after clustering.
2. **Cluster by hub/region** (group by `place.hub`; compute cluster value = sum of top scores). Choose clusters greedily by value, preferring clusters near the start city. Multi-day trips pick adjacent clusters (cluster centroid distance ≤ 350 km between consecutive clusters). Day 1 stops come from the cluster nearest the start.
3. Within each day, order stops with **nearest-neighbour + 2-opt** starting from the previous day's last stop (day 1 from the start hub). Hard-constrain `sum(visitHrs + travelHrs) ≤ maxActiveHours[pace]`. If exceeded, drop the lowest-score stop from that day and backfill it to another day if it fits.
4. Timestamp: the day begins at 08:30, with a 45-min lunch inserted when the cumulative time passes 13:00.

**C. Leg options and strategy selection:**
For each consecutive pair (including the start hub → first stop of Day 1), build all feasible `LegOption`s per Section 6.2. Compute `cost = fare + entry (separately)`, `minutes = travel + wait`, `co2 = distance × gPerKm / 1000`.
Normalise each metric within the leg (min-max over options), then:
```
cheapest : minimise cost (tie → time)
fastest  : minimise minutes (tie → cost)
greenest : minimise co2 (tie → cost); also add a +0.3 penalty weight for walking beyond tolerance
balanced : minimise 0.4*costNorm + 0.4*timeNorm + 0.2*co2Norm  (if the user priority is 'greenest', use 0.3/0.2/0.5 instead)
```
Walking above the user's tolerance is disallowed in all strategies.

**D. Totals and Eco Score:**
```
trip cost = Σ entry fees + Σ leg fares + foodCost + stayCost   (per strategy)
baselineCo2 = Σ legDistance × cab gPerKm
ecoScore = clamp(100 × (1 - co2 / baselineCo2), 0, 100)
```

Show "equals X tree-days of absorption" = `co2 / treeDailyAbsorptionKg`.

**E. Over-budget handling → `suggestions[]`:**
Compute savings for (1) switching to the cheapest strategy, (2) removing the lowest-value stop, (3) cutting a day, and (4) downgrading the stay/food tier. Return the top 3 with the savings in ₹ and an `apply` payload that the frontend sends to `/api/replan`.

**F. Replan:**
`changes` can include budget, days, walking, priority, exclude ids and interests. Re-run the full pipeline and compute a `diff` by comparing stop ids per day and the chosen mode per leg: `{removedStops, addedStops, modeChanges, costDelta, timeDelta, co2Delta}`. Render with the animated diff panel and a toast ("Saved ₹820, −1.4 kg CO₂").
